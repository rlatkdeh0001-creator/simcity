# 차량 출입 규칙 — 건물 문 앞 출현·도착 후 흐려지며 소멸 (사용자 확정 2026-11-10)

상태: **설계 확정, 구현 전.** 출동(소방·경찰·의료·영구차 등)과 이후 통근·물류·방문 차량 구현 시 공통 적용.
적용 범위: **주차 공간이 충분한 건물**의 차량 출입(소방서에 한정하지 않음). 주차가 모자라면 아래 '주차 부족' 규칙을 따른다.

## 주차 조건 (사용자 확정 2026-11-10)

- 문 앞 소멸 규칙은 **목적 건물에 그 차를 받을 주차 여유가 있을 때만** 적용한다.
- **주차가 모자라면 문 앞에서 사라지지 않는다.** 차량은 **주차장을 찾아 떠나야** 한다(주변 주차 시설로 이동 → 그곳 출입 지점에서 도착·흐려짐 소멸).
- **서비스 건물(소방·경찰·교도소·보건·교육·화장터 등)은 기본적으로 주차 부족이 생기면 안 된다.**
  자기 소속 차량은 항상 자기 건물에 수용되도록 보유 대수 ≤ 차고/주차 수용량으로 설계·검사한다.
  (서비스 차량이 아닌 방문 차량 — 예: 병원 방문객 — 의 처리는 아래 미정 항목.)
- 주차 여유 판정은 데이터로 한다: 건물별 주차 수용량(면) − 현재 주차 대수. 기존 주차 시설(4/8/16/16면)과 결합 주차장 수용량을 그대로 쓴다.

## 확정 규칙

1. **출발**: 차량은 건물 내부에서 나오지 않고, 건물의 **출입 지점(문 앞 도로 쪽 한 점)에서 나타나** 도로로 진입한다.
2. **도착**: 목적 건물의 출입 지점에 닿으면 **도착 판정**. 차량은 잠깐 **흐려지며(fade-out)** 도착을 시각적으로 알린 뒤 사라진다.
3. **흐려지는 동안의 판정**: 도착 판정 순간 차량은 **시뮬레이션·교통에서 즉시 제거**된다. 흐려지는 모습은 **순수 표시 효과**이며
   - 차선 점유, 교차로 예약, 앞차 간격(ACC) 계산, 충돌·대기열에 **포함하지 않는다.**
   - 같은 출입 지점에서 다시 출발하거나 뒤따라 들어오는 차량의 **길을 막지 않는다.**
   - 흐려지는 효과를 끄거나 속도를 바꿔도 도착 시각·차량 수·서비스 결과가 같아야 한다(전력 흐름 원과 같은 '표시/판정 분리' 원칙).
4. **차량 수 관리**: 차량은 소속 건물의 상태 데이터로 관리한다(예: 대기 N대 / 운행 중 M대). 도착·복귀하면 대기 대수로 돌아간다.
   사라진 차량은 렌더 객체만 제거되고 데이터는 유지된다.
5. **출입 지점 정의**: 건물 모양이 아니라 **정면 도로(front_road_id)·정면 방향(front_direction)** 기준으로 계산한다(BUILDING_FRONTAGE 규칙).
   도로 변경·성장으로 정면이 다시 정해지면 출입 지점도 다시 계산한다. 고속도로는 출입 지점이 되지 않는다.
6. **도로 진입**: 출현한 차량은 기존 교통 규칙(앞차 간격, 교차로 예약, 막힌 출구 진입 금지)을 따른다.
   여러 대가 동시에 출발하면 출입 지점에서 순서대로 진입한다(진입 공간이 없으면 출현 대기, 겹쳐서 생성 금지).

## 결과로 정리된 사항

- 차고 문 높이/폭과 차량 치수 불일치는 출입 판정에 영향이 없다(차량이 건물 안으로 들어가지 않음).
  소형소방서 차고 문 3.40m < 소방차 3.53m(부속 포함) 차이는 **원본 수정 없이 유지**(docs/emergency-assets-validation).
- 건물 내부 경로·주차면 내 이동 애니메이션은 구현하지 않는다(주차는 수용량 데이터로 판정).

## 구현 시 확인할 검사 (제안)

- 도착 순간 차선/교차로 예약에서 제거되는지, 흐려지는 동안 뒤 차량과 재출동 차량이 정지하지 않는지
- 흐려짐 효과 on/off·속도 변경 시 시뮬레이션 결과 동일
- 출입 지점이 정면 도로 쪽에 있고, 도로 철거·재정면 후 재계산되는지
- 동시 출발 시 겹침 없이 순서대로 진입, 차량 대수 보존(대기+운행 = 보유)
- 주차 여유 있음 → 문 앞 소멸 / 여유 없음 → 문 앞 소멸 안 하고 주차장 탐색 이동
- 서비스 건물: 보유 차량 수 ≤ 수용량 검사(모든 서비스 애셋 등록 시)

## 주차 탐색·노상 주차·보행 (사용자 확정 2026-11-10)

1. **탐색 한도 — 사용자 수정 확정(2026-11-10): 목적지에서 걷는 거리 1km 이내**의 빈 주차장을 찾는다.
   (처음 정한 '차량 이동 게임시간 1시간'은 맵 400m 기준 사실상 무제한이라 폐기.) 거리는 직선이 아니라 실제 보행 경로 길이.
   1km 보행은 약 12~15게임분(시속 4~5km) — 약속 시간에 늦을 것 같으면 아래 3번 택시 분기.
2. **못 찾으면 노상 주차**: 도로변(길거리)에 댄다. → 노상 주차는 허용(미정 4번 해결).
   노상 주차 위치·면 수, 노상 차량이 차선을 막는지 여부는 구현 시 제안.
3. **보행**: 주차 지점→목적 건물 걸어가는 시간을 계산한다. **약속 시간(출근·진료 등)에 못 맞출 것 같으면 택시를 탄다**는 분기를 만든다.
   택시 모델(taxi-sedan-01)은 있으나 택시 회사/차고 시설·요금은 아직 없음 → 택시 운영은 별도 설계 필요.
4. **주거·상업·공업 건물도 주차면을 가진다.** 단, 애셋에 따라 **주차 공간이 전혀 없는 건물도 있다**(그 경우 주변 주차장/노상).
   주거는 기본적으로 **수용 인구가 가진 차량만큼** 주차면을 둔다. 애셋별 수치는 아래 제안표.

### 확인 필요 사항 (기획 검토 결과)

- **차량 표현 비율 — 사용자 확정(2026-11-10): ② 시민 1:1 + 화면 차량만 샘플링(기본 100건당 1대).** 아래 '차량 표현·연산 절감' 절 참고.
  (검토 과정: ① 시민 기록 1개=100명 안은 주택·일자리 정원이 실제와 맞지 않아 채택하지 않음.)
- ~~게임 1시간 탐색 한도의 크기~~ → 해결: 탐색 한도를 걷는 거리 1km로 변경(위 1번). 정식 맵은 10km×10km로 확정(docs/design/MAP_SIZE_KO.md).
- **서비스 차고 수용량과 차량 수**: 사용자 확정(2026-11-10) — **주차면·차량 수는 애셋에 그려진 차고/주차선 수와 달라도 된다.**
  주차 수용량은 그림이 아니라 데이터다. 따라서 CAPACITY_PROPOSALS의 소방차 6대(소방서)·16대(광역) 제안을 유지하고,
  건물 데이터의 서비스 차량 수용량을 그 대수 이상으로 둔다(서비스 건물 주차 부족 금지 규칙 충족). 차고 칸 수에 맞춰 줄이지 않는다.
- 구급차 모델이 없다(병원 차량). 차량 애셋 추가 또는 범위 제외 결정 필요.

## 차량 표현·연산 절감 (사용자 확정 2026-11-10)

### 확정
- **시민은 1:1로 모두 시뮬레이션**한다(차 보유 여부, 출발·경로·소요·도착 시각을 시민마다 계산).
- **화면에 그리는 차만 줄인다**: 기본 비율 차량 이동 100건당 1대(설정값, 변경 가능 — '100명당 1명' 약속의 기본값).
- 그리지 않는 차도 **계산상으로는 같은 도로를 달린다**: 도로 혼잡도·주차장 점유·도착 시간은 실제 대수로 계산.
- 걷는 사람은 실제로 차가 없는 시민뿐(늦으면 택시, 이후 대중교통).
- **추적 시민 규칙**: 사용자가 시민 한 명을 클릭해 보고 있으면
  - 그 시민의 차는 샘플링과 무관하게 **무조건 화면에 그린다**(이동 중이면 즉시 실제 차량으로 승격).
  - 그 시민은 **절대 사라지지 않는다**: 샘플링·화면 밖 생략·차량 상한 정리 대상에서 제외.
  - 목적지 도착 시 차량은 기존 규칙대로 흐려지며 사라지지만, 시민 정보창은 "○○ 건물 안" 상태로 계속 추적한다.
  - (가정, 확인 필요) 이주·사망 등 시민 자체가 도시에서 없어지는 사건은 정보창에 그 사실을 남기고 추적을 종료한다.

| # | 방법 | 내용 | 효과 |
|---|---|---|---|
| 1 | **2단계 교통(보이는 차 / 안 보이는 차)** | 화면에 그리는 차만 차선·앞차 간격·교차로 예약을 매 틱 계산(미시). 나머지 이동은 "출발 시각 + 경로 소요시간 = 도착 시각"으로만 계산(거시) | 가장 큼. 대부분 이동이 차 1대당 계산 1번 |
| 2 | **도로 구간별 혼잡도 집계** | 각 구간을 지나는 실제 대수로 소요시간 계수 계산(예: 교통 공학의 BPR 식 `소요 = 기본 × (1 + 0.15 × (대수/용량)^4)`), 일정 주기 갱신 | 시민마다 충돌 계산 없이 체증 반영 |
| 3 | **사건 대기열(잠자는 시민)** | 시민을 매 틱 갱신하지 않고 다음 할 일 시각(출근·도착·귀가)에 깨움. 게임시간 순 우선순위 큐 | 시민 수가 늘어도 매 틱 비용이 거의 일정 |
| 4 | **경로 캐시** | 시민별이 아니라 출발 부지 ↔ 도착 부지 쌍 단위로 경로 저장, 도로가 바뀔 때만 무효화 | 길찾기(A*) 반복 제거 |
| 5 | **묶음 처리** | 같은 집·같은 직장·같은 시간대 이동은 한 묶음으로 계산(가구 단위 결정) | 계산 단위 축소 |
| 6 | **프레임 분산** | 하루 경계 정산·수요 재계산을 한 프레임에 몰지 않고 여러 프레임에 나눔 | 순간 끊김 방지 |
| 7 | **카메라 기준 상세도** | 화면 안 구역만 미시 교통, 화면 밖은 거시만. 추적 시민은 예외로 항상 미시 | 큰 맵에서 효과 큼 |
| 8 | **데이터 배열화** | 시민을 개별 Dictionary 대신 고정 배열(PackedArray, 시민 ID = 인덱스)로 저장. 병목이 확인되면 그 부분만 C#/GDExtension 이전 검토 | GDScript 반복문 비용 감소 |
| 9 | **화면 차량 상한** | 그리는 차 최대 대수 설정. 넘으면 비율 자동 상향(추적 시민 제외) | 렌더링 비용 상한 고정 |

권장 묶음: **1 + 2 + 3 + 4**를 3번(경제 순환)·통근 구현 시 처음부터 구조로 넣고, 6·7·9는 그 다음, 8은 측정 후 필요 시.

### 사용자 확정 (2026-11-10)

- **목표 도시 규모: 최대 인구 100만 명.**
- 연산 절감 **1(안 보이는 차는 거시 계산)** 과 **5(같은 집·같은 직장 묶음 계산)** 채택. 2·3·4는 1을 위한 기반으로 함께 구현.
- **화면 표시 차량 단계 비율** (인구 구간별, 계단식 로그형):

| 인구 구간 | 표시 비율 | 구간 끝 누적 표시 상한 |
|---|---|---|
| 0 ~ 1,000 | 1명당 1대 (전부 표시) | 1,000 |
| 1,000 ~ 10,000 | 10명 늘 때 1대 | 1,900 |
| 10,000 ~ 1,000,000 | 100명 늘 때 1대 | 1,900 + 9,900 = **11,800** |

  - 100만 명일 때 표시·미시 계산 대상 약 **11,800대**(사용자 목표 '2만 개 미만' 충족).
  - 이 값은 '동시에 미시 계산·표시할 수 있는 최대치'이며, 실제 도로 위 대수는 그 시각 이동 중인 시민 비율만큼만 쓴다.
  - 참고 대안: 100,000 이상에서 1,000명당 1대로 한 단계 더 두면 100만 명에 약 3,700대(더 가벼움). 기본값은 위 표, 구간·비율은 설정값.
  - 추적 시민의 차는 이 상한과 무관하게 항상 표시.
- **주의(구현 위험)**: 시민 기록 100만 개 자체의 계산은 차량 표시와 별개로 남는다. 사건 대기열(3)·배열화(8)를 처음부터 적용하고,
  GDScript로 목표 성능이 안 나오면 시민·교통 핵심 루프만 C#/GDExtension으로 옮기는 것을 백로그 7번에서 측정 후 결정.
목표 도시 규모(최대 인구)가 정해져야 상한값·검사 기준을 정할 수 있다(백로그 7번).
